{% note primary %}
同一 FP64 矩阵乘法中，NumPy 的 <code>A @ B</code> 可能显著快于普通 C 三重循环。差异来自实际执行路径：解释器与本地库的职责划分、循环和数据布局，以及缓存、SIMD/FMA 与执行流水线的利用。本文以这些关系为线索，讨论程序优化如何对应到体系结构约束。
{% endnote %}

<!-- more -->

## Python 标量循环与数值库调用

对于两个 {% raw %}<span>$1024\times1024$</span>{% endraw %} 双精度矩阵的乘法，直接比较 Python 与 C 的语言名称，并不足以预测运行时间。

C 的原生编译避免了解释器逐步执行的开销，但 NumPy 与普通 C 循环可能调用完全不同的计算内核。在合适的实现和规模下，前者可能获得数量级的性能优势。

这一比较首先需要确定实际承担乘加运算的代码。

`A @ B` 通常可以进入针对处理器优化的 BLAS；普通 C 三重循环则可能生成标量指令和低效访存。前者将调用开销摊销到大规模本地计算中，后者即使没有解释器开销，也可能受数据供给限制。

性能分析因此需要区分语言运行时、算法实现与硬件执行三层因素。本文逐项考察循环、数据组织和指令调度怎样影响计算资源利用，并说明这些变化为何不能简单归因于语言优劣。

矩阵乘法具有明确的数学工作量，又能体现数据复用、缓存分块、向量化和专用计算结构，适合在固定任务下比较这些实现选择。

## 一、固定计算任务与精度

考虑两个 {% raw %}<span>$N\times N$</span>{% endraw %} 的矩阵：

{% raw %}<div>$$
C=AB,\qquad C_{ij}=\sum_{k=0}^{N-1} A_{ik}B_{kj}
$$</div>{% endraw %}

以下讨论统一采用 IEEE 754 双精度浮点数（FP64），每个元素占据 8 Byte，使用传统的矩阵乘法算法，而不是 Strassen 等改变运算复杂度的方法。

计算一个输出元素需要约 {% raw %}<span>$N$</span>{% endraw %} 次乘法和 {% raw %}<span>$N$</span>{% endraw %} 次加法，因此整个计算的浮点运算量通常记为：

{% raw %}<div>$$
F\approx2N^3\ \mathrm{FLOP}
$$</div>{% endraw %}

当 {% raw %}<span>$N=1024$</span>{% endraw %} 时：

{% raw %}<div>$$
F=2\times1024^3\approx2.147\times10^9\ \mathrm{FLOP}
$$</div>{% endraw %}

以下优化保持数学工作量不变，改变的是运算组织与数据移动方式。

### 1. Python 的两种实现

先写一个最直接的版本：

```python
import numpy as np

def matmul_python(A, B):
    n = A.shape[0]
    C = np.zeros((n, n), dtype=np.float64)

    for i in range(n):
        for j in range(n):
            s = 0.0
            for k in range(n):
                s += A[i, k] * B[k, j]
            C[i, j] = s

    return C
```

它和数学定义几乎一一对应。

现在把计算替换为：

```python
def matmul_numpy(A, B):
    return A @ B
```

第一种实现由 CPython 逐次处理循环、索引、标量对象和类型运算。第二种实现从 Python 发起高层调用，再由 NumPy 连接的 OpenBLAS、Intel oneMKL 或部分平台上的 Accelerate 承担主要数值计算。两段代码因而具有不同的执行开销和优化空间。

在后一条路径中，Python 主要承担控制与调用，本地数值库负责大规模运算及硬件适配。

### 2. 测试程序与复现步骤

以下脚本在相同的 FP64 NumPy 数组上比较两种实现，避免把不同的数据结构也混入比较。[下载 Python 和 C 实验脚本](/2026/11/03/gemm-languages-to-architecture/gemm-benchmarks.zip)，解压后可运行完整示例。

```python
import time
import statistics
import numpy as np

N = 128
rng = np.random.default_rng(42)
A = rng.standard_normal((N, N)).astype(np.float64)
B = rng.standard_normal((N, N)).astype(np.float64)

def python_loop():
    C = np.zeros_like(A)
    for i in range(N):
        for j in range(N):
            acc = 0.0
            for k in range(N):
                acc += A[i, k] * B[k, j]
            C[i, j] = acc
    return C

def numpy_blas():
    return A @ B

def benchmark(fn, repeat):
    fn()  # warm-up
    samples = []
    for _ in range(repeat):
        t0 = time.perf_counter()
        fn()
        samples.append(time.perf_counter() - t0)
    return np.asarray(samples) * 1e3

np.testing.assert_allclose(
    python_loop(), numpy_blas(), rtol=1e-10, atol=1e-10
)

for name, fn, repeat in [
    ("Python loop", python_loop, 3),
    ("NumPy @", numpy_blas, 50),
]:
    samples_ms = benchmark(fn, repeat)
    median_ms = statistics.median(samples_ms)
    q25, q75 = np.percentile(samples_ms, [25, 75], method="linear")
    gflops = (2 * N**3) / median_ms / 1e6
    print(f"{name}: repeats={repeat}, median_ms={median_ms:.3f}, "
          f"iqr_ms={q75-q25:.3f}, min_ms={min(samples_ms):.3f}, "
          f"max_ms={max(samples_ms):.3f}, median_gflops={gflops:.3f}")
```

运行前可以限制 BLAS 线程数，让单线程比较更容易解释：

```bash
OPENBLAS_NUM_THREADS=1 \
MKL_NUM_THREADS=1 \
OMP_NUM_THREADS=1 \
VECLIB_MAXIMUM_THREADS=1 \
python scripts/benchmark_python.py
```

本文不预设实验跑分。加速比取决于处理器、NumPy 构建、BLAS 实现、线程配置与运行环境，应由相同条件下的测量给出。

该实验用于辨认执行路径的差异，测得倍数仅适用于记录的配置，不能作为跨平台的语言性能比例。

## 二、语言运行时与数值内核的性能边界

源代码到机器执行之间，编译器、运行时与数值库分别参与语义实现、指令生成和计算组织。

分析时应分别核查运行时承担的工作、编译器或库生成的指令，以及这些指令和访问模式对硬件的适配程度。

## 三、循环顺序与连续内存访问

固定为 C 实现后，仅改变循环次序，也可以改变缓存和预取行为。

假设矩阵按 Row-major（行优先）顺序连续存储。对于二维矩阵 `A`，元素 `A[i][j]` 在一维内存中的地址偏移为：

{% raw %}<div>$$
\mathrm{offset}(i,j)=iN+j
$$</div>{% endraw %}

这意味着相邻列元素在内存中相邻，而相邻行元素相隔 {% raw %}<span>$N$</span>{% endraw %} 个元素。

### 1. i-j-k 循环的访问模式

```c
void matmul_ijk(
    int N,
    const double *restrict A,
    const double *restrict B,
    double *restrict C
) {
    for (int i = 0; i < N; ++i) {
        for (int j = 0; j < N; ++j) {
            double sum = 0.0;

            for (int k = 0; k < N; ++k) {
                sum += A[i*N + k] * B[k*N + j];
            }

            C[i*N + j] = sum;
        }
    }
}
```

最内层循环决定连续两次访问之间的地址步长。

当 `k` 增加时，`A[i*N+k]` 在内存中连续移动，每次前进 8 Byte；但 `B[k*N+j]` 每次跨越一整行，地址前进 {% raw %}<span>$8N$</span>{% endraw %} Byte。

如果 {% raw %}<span>$N=1024$</span>{% endraw %}，那么访问 B 的步长就是 8192 Byte。

一条常见的 64 Byte Cache Line 可容纳 8 个 FP64 元素。跨行访问 B 时，单次搬入的数据可能只被部分使用；工作集较大时，数据还可能在下次复用前被替换。这降低了缓存线利用率，也增加了预取难度。

### 2. i-k-j 循环的访问模式

```c
#include <string.h>

void matmul_ikj(
    int N,
    const double *restrict A,
    const double *restrict B,
    double *restrict C
) {
    memset(C, 0, (size_t)N*N*sizeof(double));

    for (int i = 0; i < N; ++i) {
        for (int k = 0; k < N; ++k) {
            const double aik = A[i*N + k];

            for (int j = 0; j < N; ++j) {
                C[i*N + j] += aik * B[k*N + j];
            }
        }
    }
}
```

两段程序执行的都是传统矩阵乘法，复杂度同样为 {% raw %}<span>$O(N^3)$</span>{% endraw %}。

但是现在，最内层的 `j` 遍历 B 的一整行：

```text
B[k,0] → B[k,1] → B[k,2] → B[k,3] → ...
```

相应的 C 元素也被连续更新。`A[i,k]` 则被提取为一个标量，在内层循环中反复使用。

连续访问有利于硬件预取，也更容易满足编译器生成 SIMD 指令所需的规则访问条件。

`i-k-j` 同时增加了对 C 的反复更新；若活跃区域无法驻留缓存，仍会产生额外读写。因此，最佳次序依赖矩阵规模与存储层次。列优先 Fortran 数组的连续方向不同，优化次序也应相应调整。

循环重排不减少乘加次数，而是改变数据复用距离和缓存线使用方式。其收益来自访存组织，而非算法复杂度下降。

## 四、Blocking：围绕存储层次组织数据复用

连续访问改善空间局部性，但不保证反复使用的数据能够持续驻留缓存。

A、B 的元素均参与多个输出。若复用间隔超过缓存可容纳的工作范围，程序仍需反复从较慢层级读取相同数据，限制计算吞吐。

Cache Blocking（Tiling）通过分解工作集，缩短复用距离，使一组数据在被替换前完成更多运算。

### 1. 缓存分块

我们把矩阵分成多个 {% raw %}<span>$T\times T$</span>{% endraw %} 的块，对每一组块计算：

{% raw %}<div>$$
C_{\mathrm{tile}}\mathrel{+}=A_{\mathrm{tile}} B_{\mathrm{tile}}
$$</div>{% endraw %}

A、B 子块进入缓存后用于更新一批输出，以提高同一次数据搬运所支撑的乘加数量。

下面是一种简化的分块实现。为便于观察，假定 N 是 T 的整数倍，C 已预先清零。

```c
for (int ii = 0; ii < N; ii += T)
    for (int kk = 0; kk < N; kk += T)
        for (int jj = 0; jj < N; jj += T)

            for (int i = ii; i < ii + T; ++i)
                for (int k = kk; k < kk + T; ++k) {
                    double aik = A[i*N + k];

                    for (int j = jj; j < jj + T; ++j)
                        C[i*N+j] += aik * B[k*N+j];
                }
```

对于三个 {% raw %}<span>$T\times T$</span>{% endraw %} 的 FP64 子块，全部数据的名义容量为：

{% raw %}<div>$$
S=3\times T^2\times8=24T^2\ \mathrm{Byte}
$$</div>{% endraw %}

当 {% raw %}<span>$T=32$</span>{% endraw %} 时，三个子块总共约占 24 KiB；当 {% raw %}<span>$T=64$</span>{% endraw %} 时，约占 96 KiB。

名义容量只是工作集估计。相联度、其他数据占用、冲突替换与访问次序，都会影响子块能否同时驻留 L1 或 L2。

Tile Size 需要同时匹配缓存层次、寄存器资源和矩阵形状，容量增大并不意味着复用效率必然提高。

### 2. 寄存器级 Micro-kernel

高性能 BLAS 还会进一步组织寄存器级复用。

Packing 将 A、B 的部分数据转换为适合微内核读取的连续布局，Micro-kernel 则将小规模 C 子块保留在寄存器中累加。

微内核可以抽象为：

```text
Load A panel
Load B panel
Load C micro-tile into registers

for k in K dimension:
    a = A_panel[:, k]
    b = B_panel[k, :]
    C_tile += outer_product(a, b)

Store C micro-tile
```

理想情况下，C 子块在多轮 FMA 中驻留寄存器，减少 Load/Store；A、B 通过加载或广播进入向量寄存器，再用于多个输出。寄存器容量与指令调度共同限制这一复用范围。

2008 年，Goto 与 van de Geijn 在经典论文 *Anatomy of High-Performance Matrix Multiplication* 中系统解释了如何围绕多级内存层次组织 GEMM。此后的 BLIS、OpenBLAS 等实现继承并发展了这套思想。

现代 GEMM 因而通常由多层循环、数据打包和硬件相关的 Micro-kernel 组成。

外层循环安排任务分解与缓存复用，Packing 适配数据布局，Micro-kernel 组织寄存器复用、SIMD/FMA 和执行流水线。各层分别对应不同距离和容量的数据供给约束。

相同的语言表达可以进入不同的数据流和指令序列，数值库对这些层次的组织，是性能差异的重要来源。

## 五、用 Roofline 估计算力与带宽的约束

缓存命中与数据复用还需要转换为可量化的计算、带宽约束。

Roofline 使用运算量与实际数据流量建立这种对应。

Williams、Waterman 和 Patterson 提出了这个性能模型，把处理器的计算上限、内存带宽和程序的数据移动量联系在一起 [2]。

核心关系为：

{% raw %}<div>$$
P_{\mathrm{attainable}}\leq\min\left(P_{\mathrm{peak}}, B_{\mathrm{memory}}\times I\right)
$$</div>{% endraw %}

| 符号 | 物理含义 | 单位 |
| --- | --- | --- |
| {% raw %}<span>$P_{\mathrm{attainable}}$</span>{% endraw %} | 可达到的浮点计算吞吐 | FLOP/s |
| {% raw %}<span>$P_{\mathrm{peak}}$</span>{% endraw %} | 处理器峰值浮点吞吐 | FLOP/s |
| {% raw %}<span>$B_{\mathrm{memory}}$</span>{% endraw %} | 可持续内存带宽 | Byte/s |
| {% raw %}<span>$I$</span>{% endraw %} | Operational Intensity | FLOP/Byte |

此处 Operational Intensity 以实际 DRAM 流量为分母。源码中的数组访问次数不能直接代替该流量，因为缓存已经吸收了部分访问。

### 1. GEMM 的运算强度与数据复用

继续使用 {% raw %}<span>$N\times N$</span>{% endraw %} 的 FP64 矩阵。

如果假设输入最初不在缓存中、每个 A 和 B 元素都只从主存读取一次、每个 C 元素最终只写回一次，并忽略写分配等额外流量，那么：

{% raw %}<div>$$
D_{\mathrm{ideal}}=8N^2+8N^2+8N^2=24N^2\ \mathrm{Byte}
$$</div>{% endraw %}

代入传统矩阵乘法的运算量：

{% raw %}<div>$$
I_{\mathrm{ideal}}=\frac{2N^3}{24N^2}=\frac{N}{12}\quad\mathrm{FLOP/Byte}
$$</div>{% endraw %}

以 {% raw %}<span>$N=1024$</span>{% endraw %} 为例，理想流量约为 24 MiB，对应约 85.33 FLOP/Byte。

在这一理想流量假设下，DRAM 每传输一个字节能够支撑较多浮点运算，反映了矩阵乘法的数据复用潜力。

| ---: | ---: | ---: | ---: |
| 128 | 4.19 MFLOP | 0.375 MiB | 10.67 |
| 256 | 33.55 MFLOP | 1.5 MiB | 21.33 |
| 512 | 268.44 MFLOP | 6 MiB | 42.67 |
| 1024 | 2.147 GFLOP | 24 MiB | 85.33 |
| 2048 | 17.18 GFLOP | 96 MiB | 170.67 |

### 2. 代码优化与 Roofline 约束变化

重复读取主存会降低实际 Operational Intensity。此时提高 SIMD 峰值，未必改变限制程序吞吐的带宽约束。

Blocking 与 Packing 若减少主存流量，可以提高 Operational Intensity，并使计算更接近执行资源给出的上界。

进入 Compute-bound 区域以后，SIMD 利用率、FMA 吞吐、指令级并行和执行端口调度才更可能成为主要优化对象。

Roofline 仍是上界模型。寄存器溢出、依赖链、前端供给不足或负载不均衡，均可能使实际性能低于 Compute-bound 区域的理论上限。

数据移动成本与执行资源利用需要同时测量，单独改善其中一项并不足以保证接近峰值。

## 六、软件优化对应的微架构约束

循环、布局与微内核的优化，最终受向量宽度、寄存器容量、执行流水线和存储层次限制。

### 1. SIMD 的数据与依赖条件

考虑一个具有 256-bit 向量寄存器的处理器。

一个 FP64 元素占 64 bit，因此一个向量寄存器能够容纳 4 个 FP64 元素。

如果硬件支持相应的向量 FMA 指令，就可能在一条向量指令中完成：

{% raw %}<div>$$
C_{0:3}\leftarrow A_{0:3}\times B_{0:3}+C_{0:3}
$$</div>{% endraw %}

按照每次乘法与加法分别记为一个 FLOP 的约定，这相当于 8 FLOP。

SIMD 指令可用，并不意味着编译器一定能够对目标循环向量化。

编译器需要证明访问规律、迭代依赖与内存别名允许向量执行，还需评估控制和数据整理开销是否抵消收益。

这也解释了为什么循环重排、数据类型和 `restrict` 等信息能够影响最终代码，即使 CPU 的 ISA 完全没有变化。

### 2. 独立累加器与 FMA 流水线

假设一段计算不断更新同一个累加器：

```c
sum = fma(a0, b0, sum);
sum = fma(a1, b1, sum);
sum = fma(a2, b2, sum);
```

每次更新依赖前次结果，形成串行数据依赖。

即使存在多个 FMA 单元，可发射操作的数量也可能受依赖链延迟限制。

多个独立累加器能够提供并行就绪操作，使不同 FMA 同时处于执行流水线中。

这正是 GEMM Micro-kernel 常常在寄存器中维护多个输出元素的原因之一。

AMD 在一篇 AOCL-BLAS 优化文章中讨论了 FMA 依赖链、指令前端、μOp Cache 和微内核结构的影响 [6]。这类工作已经不再是简单调整高级语言语法，而是在针对具体微架构优化指令组织。

成熟内核的改进幅度可能仅为几个百分点，对应此前未被充分利用的资源。具体性能需要依据厂商测试条件解释，不能将不同平台、规模与线程设置下的数字直接组合比较。

### 3. 缓存容量、命中率与访问代价

缓存容量影响复用机会，但仍需与访问时间和实现代价一起评估。

增加容量可能增加面积、功耗和访问延迟，不能将命中率改善单独等同于程序加速。

更大的缓存可能提高数据命中率，却也可能增加访问延迟和芯片面积。更宽的向量执行单元能提高理论吞吐，但需要更高的数据供给能力、更复杂的寄存器文件及配套数据通路。

多核共享缓存还涉及带宽争用、缓存一致性、NUMA 和线程调度。

计算资源与存储容量应围绕目标工作负载配置，使执行吞吐和数据供给保持匹配。

### 4. CPU、GPU 与矩阵加速器的执行结构

GEMM 的数据流需求包括输入复用、跨多次累加保留输出，以及减少外部内存流量。不同处理器通过不同的资源组织满足这些需求。

GPU 将其映射到线程块、Shared Memory、寄存器分块和专用矩阵指令。

以 NVIDIA A100 为例，它不仅提供常规 FP64 执行能力，也提供支持 FP64 矩阵运算的 Tensor Core 路径。NVIDIA 公布的相关峰值分别为 9.7 TFLOP/s 和 19.5 TFLOP/s [7]。

上述数值只对应 A100 的 FP64 路径。不同 GPU 的 FP64 吞吐、Tensor Core 精度支持均可能不同，消费级 FP32/FP16 峰值不能直接用于估算 FP64 DGEMM。

对于适合规则数据流的矩阵运算，专用硬件还可以进一步采用 Systolic Array 等架构，让操作数沿着计算单元阵列传播，在局部完成多次乘加。

CPU 上的 Blocking 是在软件中安排数据复用；专用加速器则可以把这种复用关系直接组织成片上 SRAM、寄存器和计算单元之间的硬件数据流。

矩阵加速器因此需要同时组织算术单元与局部数据流，乘法器数量不能独立决定有效吞吐。

## 七、从 DGEMM 数据流到 FPGA 结构设计

新增指令、向量宽度和频率描述计算能力，却不能单独说明操作数能否持续到达。

表中将 DGEMM 的优化需求对应到具体硬件资源。

| 软件中发现的问题 | 体系结构中的对应设计 |
| --- | --- |
| 逐元素操作的调度开销很高 | 向量指令、专用矩阵指令、低开销执行模型 |
| 相同数据反复从主存加载 | 多级 Cache、Scratchpad SRAM、数据复用 |
| 访存不连续 | Cache Line、预取器、连续访问与合并访存 |
| FMA 之间存在串行依赖 | 多累加器、流水线、指令级并行 |
| 多线程争用共享资源 | 缓存分层、内存通道、NUMA、调度机制 |
| 大规模数据搬运限制效率 | 更高带宽、局部存储、计算与搬运重叠 |

假设我们准备在 FPGA 上实现一个矩阵乘法加速器。

增加乘法器提高理论峰值；若片外 DDR 无法提供足够操作数，新增单元仍受数据供给限制。

将输入缓冲到片上 BRAM，并结合分块与流水复用，可能在较少算术资源下获得更高实际吞吐。

该方案仍需核查 BRAM 端口、Banking 冲突、目标 Initiation Interval，以及缓冲的面积、功耗和布线成本。

Blocking 在硬件中的实现，涉及存储组织、并行度和数据通路的联合设计。

数据流确定后，存储容量、算术单元和控制逻辑仍需要共同配置，避免局部资源扩张将瓶颈转移到其他模块。

这套思路也适用于 AI 推理中的矩阵乘法、Attention、卷积，以及许多其他高吞吐计算模块。

## 八、性能实验的控制条件与测量误差

矩阵乘法的加速比容易受到数据结构、线程数和计时边界影响。

比较 Python、C、Rust、Julia 或不同 BLAS 后端，应首先对齐任务和测量条件。

输入维度、FP64 精度、布局和线程数应保持一致；分配、JIT 首次编译、Packing 与 CPU/GPU 传输是否计时也应明确。否则，测量差异无法归因到目标实现。

多次运行应报告中位数和离散程度，并保留编译器版本、编译选项及 BLAS 后端信息。下载附件中的 C 与 Python 脚本默认各重复 5 次，均输出原始样本、`repeats`、`median_ms`、`iqr_ms`、`min_ms`、`max_ms`、`best_ms` 和按中位耗时计算的 `median_gflops`。IQR 为第 75 与第 25 百分位数之差，按排序后位置 `(n-1)×q` 线性插值；`best_ms` 单独表示最小耗时。运行环境写入标准错误流，可与结果一并保存；附件 README 给出完整命令。对于 CPU，可以结合 `perf` 或其他性能计数器观察周期数、指令数、缓存行为和硬件资源利用情况。

计算吞吐通常使用：

{% raw %}<div>$$
\mathrm{GFLOP/s}=\frac{2N^3}{T_{\mathrm{seconds}}\times10^9}
$$</div>{% endraw %}

GFLOP/s 便于与执行资源吞吐对照，总运行时间则反映任务完成成本，两项指标应同时保留。

小矩阵可能由固定调用成本主导，大矩阵则更多受到缓存、带宽和计算吞吐约束。单一 N 下的性能次序，不能直接推广到其他规模。

计算结果的数值语义也属于实验条件。

浮点加法不满足严格的结合律，FMA 也可能改变中间舍入过程。因此，改变循环顺序、进行向量化或并行归约后，两段正确的 FP64 矩阵乘法程序未必产生逐位相同的结果。

正确性验证应依据任务要求检查误差、稳定性和可重复性，并明确是否要求逐位一致。

## 九、执行路径与瓶颈迁移

NumPy 快于普通 C 循环的现象，应根据实际内核与数据路径解释。

运行时决定任务如何交给执行系统，编译器与数值库决定指令和数据组织，微架构则决定可达到的吞吐、带宽和延迟。三层约束共同形成运行时间。

同一语言可以通过布局、循环、分块、向量化和并行度改变性能，但一次局部优化的收益依赖其对应约束仍占主要比例。

解释器开销降低后，缓存访问可能成为限制；访存改善后，SIMD 与执行单元利用可能成为限制。更高计算利用率又可能增加带宽、功耗或线程扩展压力，因此优化后需要重新测量并检查瓶颈迁移。
